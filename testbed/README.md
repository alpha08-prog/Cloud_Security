# testbed/

The IsoLab multi-tenant testbed: one Compose project, two profiles.

| File | What it is |
|---|---|
| `compose.yaml` | Provider plane (socket proxy, auditor, canary, Prometheus, Grafana) plus bare tenant definitions with **no** security settings |
| `compose.insecure.yaml` | Overlay: a deliberately weak lift-and-shift baseline |
| `compose.hardened.yaml` | Overlay: the controls derived from the paper's p.16 requirements (R1–R4) |
| `policy.yaml` | What the auditor considers "good": required labels, sensitive paths, version baseline, provider exceptions, gate threshold |
| `waivers.yaml` | Accepted, time-boxed exceptions (each with a reason, platform and expiry) |
| `images/` | Tenant, canary and load-generator images (digest-pinned bases) |
| `cpus.env`, `secrets/` | Generated by `scripts/lab.py`; git-ignored |

Always drive it through `python scripts/lab.py` (`up`, `audit`, `demo`, `down`, …). It plans the
CPU placement and creates the secrets before calling Compose.

## Safety: read before running the insecure profile

The insecure profile is **genuinely insecure on the machine that runs it**:

- `tenant-c` is privileged, shares the host's PID and IPC namespaces and holds the Docker socket,
  which is equivalent to root on the container host.
- Tenants share a routable network with the provider plane.

What limits the risk:

- Everything is bound to `127.0.0.1`.
- `tenant-c` only idles: there is no exploit or attack code anywhere in this repository.
- Host `/etc` is mounted read-only and `/` is never mounted.

Run it only on your own laptop or an ephemeral CI runner, never on a shared host, and run
`python scripts/lab.py down` when you're done.

The hardened profile also applies two provider-side kernel settings to the container host
(`kernel.kptr_restrict=1`, `kernel.dmesg_restrict=1`). On Docker Desktop they reset when Docker
Desktop restarts.
