## Details

### ISO-01 Workload is not privileged

A privileged container has every capability and direct access to host devices; its isolation from the host and from other tenants is nominal.

- **Remediation:** Remove `privileged: true`; grant only the specific capability a workload needs, if any.
- **CSA Top Threats:** 4 · **CSA domains:** virtualization · **ENISA:** technical · **NIST:** cloud-provider

### ISO-02 Capabilities dropped to the minimum

Linux capabilities split root's power into pieces. Tenants should drop all of them and add back only what the policy allows.

- **Remediation:** Set `cap_drop: [ALL]` and keep `cap_add` within the policy allowlist.
- **CSA Top Threats:** 4 · **CSA domains:** virtualization · **ENISA:** technical · **NIST:** cloud-provider, consumer

### ISO-03 Syscall filter on, privilege gain blocked

The engine's default seccomp profile blocks dangerous syscalls (shrinking the shared-kernel attack surface); no-new-privileges stops setuid binaries from gaining privileges.

- **Remediation:** Never run with `seccomp=unconfined`; add `no-new-privileges:true` to `security_opt`.
- **CSA Top Threats:** 4 · **CSA domains:** virtualization · **ENISA:** technical · **NIST:** cloud-provider

### ISO-04 Runs as a non-root user

Root inside a container is root on the shared kernel for anything that escapes the namespace.

- **Remediation:** Set a numeric non-root `user:` (e.g. 10001) or a non-root USER in the image.
- **CSA Top Threats:** 4 · **CSA domains:** identity-and-access-management · **ENISA:** technical · **NIST:** consumer

### ISO-05 Private process and hostname namespaces

Sharing the host PID or UTS namespace lets a workload see and signal every process on the host.

- **Remediation:** Remove `pid: host` and `uts: host`.
- **CSA Top Threats:** 4 · **CSA domains:** virtualization · **ENISA:** technical · **NIST:** cloud-provider

### ISO-06 CPU, memory and process limits set

Without limits one tenant can exhaust CPU, memory or PIDs for everyone on the host (the noisy neighbour of experiment E1). Swap must be capped too, or memory limits leak into shared swap.

- **Remediation:** Set `cpus`, `mem_limit` equal to `memswap_limit`, and `pids_limit`.
- **CSA Top Threats:** 1, 4 · **CSA domains:** virtualization, traditional-security-business-continuity-and-disaster-recovery · **ENISA:** technical · **NIST:** cloud-provider

### ISO-07 Dedicated CPU sets per tenant

The paper asks for 'adequate separation of dedicated resources'. Each tenant gets its own CPUs; no two tenants' CPU sets overlap.

- **Remediation:** Give every tenant a `cpuset`; generate them with `lab.py cpus` so they never overlap.
- **CSA Top Threats:** 4 · **CSA domains:** virtualization · **ENISA:** technical · **NIST:** cloud-provider

### HV-01 Engine API not exposed to workloads

The container engine is this testbed's hypervisor. Whoever holds its socket controls every workload on the host.

- **Remediation:** Never mount docker/containerd sockets into workloads; give monitoring a read-only API proxy instead.
- **CSA Top Threats:** 2, 3 · **CSA domains:** virtualization, identity-and-access-management · **ENISA:** technical · **NIST:** cloud-provider
- **Platform notes:** The provider's socket-proxy is the single documented exception.

### HV-02 Engine and kernel at the patch baseline

The shared kernel and engine are the 'hypervisor' every tenant depends on; they must be at or above the policy's minimum versions.

- **Remediation:** Upgrade Docker Engine / the host kernel to the versions in policy.yaml.
- **CSA Top Threats:** 4 · **CSA domains:** virtualization, data-center-operations · **ENISA:** technical · **NIST:** cloud-provider

### HV-03 CPU vulnerability mitigations active

The kernel reports, per known CPU flaw, whether it is mitigated. A 'Vulnerable' entry is a shared-hardware weakness every tenant inherits and none of them can fix.

- **Remediation:** Update host microcode/firmware and the kernel; this is the provider's responsibility.
- **CSA Top Threats:** 4 · **CSA domains:** virtualization · **ENISA:** technical · **NIST:** cloud-provider
- **Platform notes:** Virtualised hosts (WSL2, cloud VMs) cannot load microcode themselves: expect waivers there.

### HV-04 User-namespace isolation enabled

With user namespaces (userns-remap or rootless mode) root in a container maps to an unprivileged user on the host, so an escape lands without privileges.

- **Remediation:** Enable `userns-remap` in daemon.json or run the engine rootless.
- **CSA Top Threats:** 4 · **CSA domains:** virtualization · **ENISA:** technical · **NIST:** cloud-provider
- **Platform notes:** Docker Desktop offers this only with Enhanced Container Isolation (Business tier).

### HV-05 Mandatory access control profile applied

AppArmor/SELinux confine what a process may touch even as root. Applies where the host supports it.

- **Remediation:** Keep the engine's default AppArmor profile (`docker-default`); never set `apparmor=unconfined`.
- **CSA Top Threats:** 4 · **CSA domains:** virtualization · **ENISA:** technical · **NIST:** cloud-provider
- **Platform notes:** Skipped on hosts without AppArmor or SELinux (e.g. Docker Desktop).

### HV-06 Host kernel hardening settings

Kernel settings that hide kernel addresses and logs from unprivileged users and restrict eBPF and performance counters on the shared kernel.

- **Remediation:** Set the sysctls listed in policy.yaml (lab.py applies them when bringing up the hardened profile).
- **CSA Top Threats:** 4 · **CSA domains:** virtualization · **ENISA:** technical · **NIST:** cloud-provider

### DL-01 No sensitive or writable host mounts

Bind-mounting host paths into a tenant exposes host or other tenants' data and, if writable, lets the tenant alter it.

- **Remediation:** Use named volumes owned by the tenant; never bind host system paths.
- **CSA Top Threats:** 5 · **CSA domains:** information-management-and-data-security, virtualization · **ENISA:** technical · **NIST:** cloud-provider

### DL-02 No storage shared between tenants

A volume mounted by two tenants is a direct data channel between them.

- **Remediation:** Give each tenant its own volume, labelled with its tenant id.
- **CSA Top Threats:** 5, 4 · **CSA domains:** information-management-and-data-security · **ENISA:** technical · **NIST:** cloud-provider

### DL-03 No shared IPC namespace

Sharing the host's (or another tenant's) IPC namespace exposes shared memory segments and queues.

- **Remediation:** Remove `ipc: host`; never join another tenant's IPC namespace.
- **CSA Top Threats:** 4, 5 · **CSA domains:** virtualization · **ENISA:** technical · **NIST:** cloud-provider

### DL-04 Read-only root filesystem

An immutable root filesystem stops a compromised workload from altering its own code or planting files; writable state lives only in declared volumes and tmpfs.

- **Remediation:** Set `read_only: true` and mount a small tmpfs for /tmp.
- **CSA Top Threats:** 5 · **CSA domains:** application-security · **ENISA:** technical · **NIST:** consumer

### DL-05 No secrets in environment variables

Environment variables leak through `inspect`, crash dumps and child processes. Only variable names are checked and reported, never their values.

- **Remediation:** Pass secrets as files (Compose secrets) and read them at runtime.
- **CSA Top Threats:** 5 · **CSA domains:** encryption-and-key-management · **ENISA:** technical · **NIST:** consumer

### XVM-01 No network shared by two tenants

Tenants on a common network can reach each other directly, so one compromised tenant can attack the others.

- **Remediation:** Put each tenant on its own network; route any necessary traffic through a provider gateway.
- **CSA Top Threats:** 4 · **CSA domains:** virtualization · **ENISA:** technical · **NIST:** cloud-provider

### XVM-02 Tenant networks are internal

Tenant networks without egress cannot exfiltrate data or reach the default bridge where other workloads may live.

- **Remediation:** Mark tenant networks `internal: true`; never attach tenants to the default `bridge`.
- **CSA Top Threats:** 5, 4 · **CSA domains:** traditional-security-business-continuity-and-disaster-recovery · **ENISA:** technical · **NIST:** cloud-provider

### XVM-03 No host network namespace

With the host's network stack a workload can reach every service on the host and every tenant.

- **Remediation:** Remove `network_mode: host`.
- **CSA Top Threats:** 4 · **CSA domains:** virtualization · **ENISA:** technical · **NIST:** cloud-provider

### XVM-04 Tenants publish no host ports

A published port is a path around network segmentation (other tenants can reach it via the host) and, on 0.0.0.0, exposes the tenant to the LAN.

- **Remediation:** Do not publish tenant ports; expose services through the provider's ingress.
- **CSA Top Threats:** 6, 4 · **CSA domains:** traditional-security-business-continuity-and-disaster-recovery · **ENISA:** technical · **NIST:** cloud-provider

### XVM-05 No physical core shared by two tenants

SMT (hyper-threading) siblings share a core's caches and execution units. Tenants that share a physical core are not separated in hardware, which is what cross-VM attacks rely on.

- **Remediation:** Plan CPU sets on physical-core boundaries (lab.py cpus), or disable SMT for sensitive workloads.
- **CSA Top Threats:** 4 · **CSA domains:** virtualization · **ENISA:** technical · **NIST:** cloud-provider
- **Platform notes:** Inside a VM the core topology is virtual, so this check is indicative there.

### XVM-06 Memory deduplication (KSM) off

Kernel same-page merging makes identical memory pages of different tenants physically shared.

- **Remediation:** Keep /sys/kernel/mm/ksm/run at 0 on multi-tenant hosts.
- **CSA Top Threats:** 4 · **CSA domains:** virtualization · **ENISA:** technical · **NIST:** cloud-provider

### XVM-07 Cross-tenant tripwires armed

The paper asks solutions to 'examine any attempt of exploiting cross-VM and data leakage'. That needs live detection: the engine-event watcher running, the canary healthy, alert rules loaded.

- **Remediation:** Keep the auditor service, the canary and Prometheus rules running.
- **CSA Top Threats:** 3, 4 · **CSA domains:** incident-response-notification-and-remediation · **ENISA:** technical · **NIST:** auditor

### ID-01 Every workload carries an identity

The paper's first requirement: 'virtual machine identification'. Each workload declares its plane, tenant, owner and a unique workload id.

- **Remediation:** Add the io.isolab.* identity labels (see policy.yaml).
- **CSA Top Threats:** 7 · **CSA domains:** governance-and-risk-management · **ENISA:** policy-organizational · **NIST:** cloud-provider, consumer

### ID-02 No unattributed workloads on the host

Anything running on the host without an identity is outside every control (CSA's 'unknown risk profile').

- **Remediation:** Label or remove the workload; list sanctioned exceptions in policy.yaml.
- **CSA Top Threats:** 7, 1 · **CSA domains:** governance-and-risk-management · **ENISA:** policy-organizational · **NIST:** auditor

### ID-03 Identity matches network and storage placement

A workload labelled as tenant X must only be attached to tenant X's networks and volumes.

- **Remediation:** Label networks and volumes with their tenant and attach workloads only to their own.
- **CSA Top Threats:** 4 · **CSA domains:** virtualization · **ENISA:** technical · **NIST:** cloud-provider

### ID-04 Image provenance recorded

Knowing exactly what runs: images are pinned by digest, or built from a digest-pinned base and labelled with their source revision.

- **Remediation:** Pin `image:` by @sha256 digest; build from pinned bases with OCI revision/base labels.
- **CSA Top Threats:** 7 · **CSA domains:** application-security · **ENISA:** technical · **NIST:** consumer

### ID-05 Every tenant continuously observed

The paper asks for 'constant observation of shared' resources: every tenant must have fresh usage and pressure samples.

- **Remediation:** Keep the auditor running; make sure its cgroup mount is present so pressure (PSI) is readable.
- **CSA Top Threats:** 7 · **CSA domains:** compliance-and-audit · **ENISA:** technical · **NIST:** auditor
